# COWMATA 活动量综合决策模块 v1.0.0

本文路径均以模块根目录为基准，命令也在模块根目录执行。

本目录可独立运行，将原始 V2 尾环 IMU 转为活动特征、活动证据等级和综合算法输入。运行仅依赖 Python ≥3.8、NumPy ≥1.20，不依赖之前的分析脚本或温度模块。

已在现有10头牛、500个原始JSON、88,311,001帧上实测。活动计算及逐牛提示结果复现上一轮优化版。模块的等级表示活动证据强弱，不是产犊概率；当前任务是为温度、抬尾、起卧、努责等综合判断提供活动输入。

## 直接接入

在模块根目录执行 `python -m pip install .`，或将整个 `cowmata_activity_aux` 文件夹复制到综合算法项目。

```python
from cowmata_activity_aux import ActivityModule, Context, as_fusion_features

# cow_id 等变量由业务系统的本次牛—设备绑定提供；时间为 Unix 毫秒整数。
module = ActivityModule(Context(
    cow_id=cow_id,
    device_id=device_id,
    binding_id=binding_id,
    binding_start_ms=binding_start_ms,
))

# sensor_json 是 json.loads(...) 得到的原始传感器字典。
result = module.process_packet(
    sensor_json,
    received_at_ms=server_received_ms,
    evaluated_at_ms=now_ms,
)
fusion_input = as_fusion_features(result, now_ms=now_ms)

# 无新包时可查询；不插值生成活动，不产生新的提示事件。
result = module.snapshot(later_ms)
fusion_input = as_fusion_features(result, now_ms=later_ms)
```

一个绑定一个实例；同一实例按处理时间串行调用。换牛、换设备、重新佩戴并建立新绑定、或新一轮孕期，应新建实例。若配置加速度标定值，也应在新的绑定开始时指定。

实际接入必须传服务器接收时间。仅离线回放时允许使用JSON的 `update_time` 代理，并传 `receive_time_source='json_update_proxy'`。有排队延迟时，`evaluated_at_ms` 使用实际作出决定的时间；提示不倒填到接收之前或包内采样时刻。

## 综合算法读取什么

推荐使用 `as_fusion_features`，字段如下。

| 字段 | 含义 |
|---|---|
| `activity_ratio` | 最近一小时活动 / 自身动态基线，主输入 |
| `activity_excess_ratio` | 比基线增加的比例，例如0.5表示增加50%；与ratio等价，二者选一个入模 |
| `activity_level` | LOW、ELEVATED、STRONG；数据不适用时UNAVAILABLE |
| `activity_available` | 当前是否达到基本覆盖、历史和时效要求 |
| `activity_coverage_1h` | 当前特征小时的有效观测占比 |
| `activity_reference_quality` | SAME_CLOCK_BLEND、PROVISIONAL_SAME_DAY或INSUFFICIENT_HISTORY |
| `activity_reference_days` | 可用同钟点历史天数，0～3 |
| `activity_reference_valid_hours` | 较宽历史参考中的有效观测小时数 |
| `activity_observation_age_seconds` | 距最后实际采样的秒数 |

`activity_available=False` 时，ratio为 `None`。它不表示活动为零，也不能用于否决其他模态的提示。同日临时基线仍可提供辅助证据，但应将历史质量一并送入综合判断。

完整 `result` 另外包含：

- `new_activity_evidence`：本次真实新包是否新开启R≥1.5的活动证据事件。
- `new_strong_activity_evidence`：是否新开启R≥2的强活动证据事件。
- 对应 `activity_event_id` / `strong_activity_event_id`：业务持久化和通知去重使用。
- `features`：1/3/6小时活动、基线、比例、覆盖率和历史信息，用于解释及审计。
- `last_update`：最近采样范围、接收时间来源、帧数、包内缺口、有效时长和饱和计数。
- `quality_status`：VALID、PROVISIONAL、NO_DATA、INSUFFICIENT_HISTORY、LOW_COVERAGE、BASELINE_TOO_LOW、STALE_DATA或PHASE_INACTIVE。

两档事件来自同一活动指标，是不同强度门槛的观察结果。综合算法使用一个连续ratio即可；不要将两档事件或ratio与excess重复计分。`calving_probability`、`eta_hours` 固定为空。

## 固定计算方法

1. 解码22字节 `<I9h>` 帧，只使用前三轴加速度。默认4096 counts/g为名义换算，尚非本批设备独立标定结果。支持完整V2包；异常前缀、残缺帧和时间回退明确报错，不静默删点。
2. 包内相邻时间差超过100ms即分段。仅在连续段内按50Hz重采样，以各轴100点后向均值估计重力，计算剩余三轴向量模长VeDBA。每次分段前99点不计入有效活动。不同完整上传包分别重置，与此前验证口径一致；接口不用于任意切碎的帧流。
3. 先按真实分钟累计活动和有效样本数，再计算1小时有效时间加权平均。当前小时覆盖不足65%时不给出可用ratio。PPG采样造成的空挡保留，无观测部分不补零、不进入平均分母。
4. 基线参考 `[t−25h,t−1h]`，排除当前一小时；对至少有42秒有效观测的参考分钟按有效时长加权。至少2小时参考跨度、1.5小时有效参考、90个合格参考分钟才启动。
5. 取过去1、2、3天同钟点1小时活动的中位数，已有n天时，其权重为 `n/(n+2)`；其余权重给较宽历史均值。没有同钟点历史则使用同日临时基线。基线随有效历史动态更新。
6. `R=A1h/B`。B低于名义0.005g时不计算比值。R≥1.5输出ELEVATED，R≥2输出STRONG，否则LOW。3/6小时活动供解释，不作为必须持续上升的门槛；高活动分钟占比未纳入重复评分。

时窗对齐到最新采样所属分钟的结束边界，只使用已经收到的点；最后不足一分钟的未采部分没有虚构观测。`feature_window_end_ms` 是分桶边界，`data_through_ms` 才是最后实际采样时刻。定时快照保留最后真实窗口的特征，不能把它理解成新采集的当前一小时数据。

两档分别检测越过门槛后的新事件，同档至少间隔120分钟，持续处于门槛以上不重复提示。超过120分钟无合格更新后，下一次真实数据重新判断。较低门槛可能在目标窗之前就已持续触发，因此不同门槛的“窗内新提示时间”不保证高门槛总是更晚。

距最后实际采样超过90分钟，输出STALE_DATA、不可用于当前活动决策。90分钟是适配目前约一小时整包上传的工程时效上限，非生物学最优值。快照、重复包和拒收包不产生新事件。

`Config` 支持显式配置，默认参数同时列在 `示例/config.example.json`。该JSON供接入参考，不自动加载；修改时需通过 `Config(**settings)` 传入，并重新验证。已验证的预处理固定为50Hz/100点。

## 输入异常与持久化

必需输入字段：`device`、`uid`、`version=2`、`create_time`、`imu`。温度、PPG和标注字段不参与推断。最长支持两小时采集包。`PacketError.code` 标识设备不符、非法Base64、重复时间戳、未来采样等；校验失败不修改历史或事件状态。

同UID、同IMU及采样起点返回DUPLICATE_IGNORED；同UID但不同信号拒收。已处理采样范围内的迟到或重叠包返回LATE_OR_OVERLAP_IGNORED，不改写旧决定。内存保留最近96小时分钟统计和最多2048个UID指纹；更早的重传依然由采样范围检查拦截。

```python
state_text = module.to_state_json()  # 同时持久化本次result/事件，业务侧保证一致提交
module = ActivityModule.from_state_json(state_text)

# 业务系统确认进入产犊或产后后，关闭产前活动输出：
result = module.set_phase('calving', at_ms=now_ms)
result = module.set_phase('postpartum', at_ms=later_ms)
```

状态包含配置、分钟统计、历史来源、已处理UID和事件状态。加载时校验版本、时间和数值一致性，并从分钟统计重算特征。阶段只能前进；新孕期使用新绑定。服务端需对同绑定加锁，并将状态和待投递事件一并保存；仅保存状态后崩溃再重试，可能漏掉尚未投递的事件。

## 命令行例子

`示例/example.py` 支持原JSON、快照和阶段关闭，以临时文件原子替换保存状态。尖括号内容替换为实际参数。

```text
python 示例/example.py --packet <JSON路径> --state <状态路径> --received-ms <服务器接收毫秒> --now-ms <决策毫秒> --cow <耳标> --device <设备号> --binding <本次绑定ID> --binding-start-ms <绑定起始毫秒>
python 示例/example.py --snapshot --state <状态路径> --now-ms <当前毫秒>
python 示例/example.py --phase postpartum --state <状态路径> --now-ms <当前毫秒>
```

首次之后可省略绑定参数；若仍提供，示例会检查是否与状态一致。离线原包测试可用 `--offline-update-time` 替代 `--received-ms`。返回值同时包含完整result与简洁fusion字段。

## 原始数据实测

本模块从原始JSON重新解码计算，没有拿旧特征表代替推断。先完成全部逐包推断，再载入露蹄/完全娩出标签评价。结果文件在 `验证/结果`。

| 指标 | R≥1.5活动证据 | R≥2强活动证据 |
|---|---:|---:|
| 10头牛中目标窗内新开启提示 | 8/10 | 5/10 |
| 较早时段提示次数 | 18 | 7 |
| 较早时段有效观测小时 | 217.77 | 217.77 |
| 较早提示/24有效观测小时 | 1.98 | 0.77 |

目标窗为 `[完全娩出前6小时，露蹄)`，以文件更新时间作为离线可用时刻代理。较早提示指该6小时窗之前的提示；分母按可计算更新所属数据包的有效观测时长汇总，不是完整日历监测天数或独立健康对照的临床误报率。

两头未出现活动提示的22146、23132，临产时都只有约1.9小时有效参考历史；22225仅早于露蹄约6分钟。这批牛已参与此前算法探索，8/10不能称为独立预测准确率。此前限制背景提示并留一牛选择规则的探索性结果为4/10；本次交付验证检验的是固定模块与原始数据的可复现性，没有重新调参提高命中数。

运行以下命令可复现测试与本批实测：

```text
python -m unittest discover -s 验证/tests -v
python -X utf8 验证/脚本/validate_real_data.py
```

回放脚本默认寻找父目录下的正常数据、标签及原v1/v2分析目录，也支持 `--data-root`、`--labels`、`--reference-v1`、`--reference-v2`、`--out` 指定路径。旧分析仅用于最后对照，不是运行模块的依赖；核心模块无需标签。

本批核验包括500包源文件哈希、88,311,001帧、474.79小时有效活动、4,500项特征一致性对照、逐牛两档事件对照，以及112次恢复、112次重传、122次快照检查。特征最大绝对差约8.8×10⁻¹⁴。完整数字见 `验证/结果/validation_summary.json`，输出规范见 `cowmata_activity_aux/output.schema.json`。

交付核验另外通过17项测试、507个输出Schema检查，以及独立安装、原JSON命令行处理、状态重启和错误换绑拒绝。简洁汇总见 `说明/实测报告.md`。
